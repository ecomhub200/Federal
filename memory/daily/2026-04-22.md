### Session (afternoon) - Fix tier scope key + boundary cleanup for PD/City tiers

**Context:** PR #5 (`claude/implement-tier-navigation-LjD9N`, merged as `4595436`) added Planning District and City/Town handlers to the tier navigation system in `app/index.html`. User flagged two bugs that slipped through review and asked for a fix on branch `claude/fix-tier-scope-key-KDpje`.

**Key Exchanges:**
- User: "Found a real bug risk: `getTierScopeKey()` doesn't handle 'planning_district' or 'city'. Fix it now."
- Investigated the function at `app/index.html:21792`. Confirmed that `'city'` was grouped with `'county'` returning `county_${fullFips}`, and `'planning_district'` had no case at all (fell through to the same default).
- Traced the consumers: both `handlePlanningDistrictSelection()` (line 21229) and `handleCitySelection()` (line 21294) dispatch a `tierChanged` CustomEvent whose `detail.scopeKey` is computed by `getTierScopeKey()`. Downstream listeners (school / transit / AI tabs) were receiving a stale `county_<fips>` scope while the user viewed a PD or City.
- Also noticed a sibling bug: `handleTierChange()` at line 20896 cleared MPO / Region / state-outline / county-jurisdiction overlays on every tier switch, but never called `removePlanningDistrictBoundaryLayer()` or `removeCityBoundaryLayer()`. Switching tiers from a PD (teal) or City (amber) left the stale overlay on the map.

**Decisions Made:**
- **Scope**: fix only the two bugs called out. Did NOT touch `getTierScopeName()` at line 21812 (same shape bug — city grouped with county, no planning_district case) because it was out of scope. Flagged in commit message and user report as a follow-up.
- **Field names**: read the selection handlers rather than guessing. Planning District id lives at `jurisdictionContext.tierPlanningDistrict.id` (set line 21242–21244). City id lives at `jurisdictionContext.tierCity.id` (set line 21307; the id is actually the slug).
- **Clearing convention**: added `removePlanningDistrictBoundaryLayer()` and `removeCityBoundaryLayer()` unconditionally alongside the existing MPO/Region clears in `handleTierChange`. Matches the pattern used by per-tier selection handlers (21249–21255, 21312–21318), which clear all sibling boundaries and then redraw their own.
- **Testing**: extended `tests/test_boundary_display.js` (a node script that regex-greps function bodies from `index.html` and asserts on contents) rather than introducing jsdom. Added 2 assertions to Section 7 and a new Section 7b with 4 assertions. Full suite: 3172/3172 pass.

**Lessons Learned:**
- Switch statements that use `case 'a': case 'b': default:` to collapse multiple tiers into one branch are a trap when new tiers get added — the fall-through is silent and the new tier gets wrong data. Explicit case-per-tier with a single true default is safer.
- When adding a new tier to this navigation system, there are at least five sites that must be updated in lockstep: (1) `getTierScopeKey`, (2) `getTierScopeName`, (3) `handleTierChange` clearing block, (4) a per-tier `handle{Tier}Selection` handler that clears siblings and redraws, (5) a `remove{Tier}BoundaryLayer` helper.
- PR #5 updated 3, 4, 5 but missed 1 and 2. A pre-merge checklist of these five sites would catch this pattern.
