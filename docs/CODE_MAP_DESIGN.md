# Crash Lens Code Map — Design Doc

**Status:** Approved approach (2026-05-19). Replaces modular extraction as the PRIMARY CC navigation aid. Modular extractions already done stay; new modular extractions are now optional.

## The core insight

The modular refactor was solving the WRONG problem.

- ❌ **Wrong problem:** "the file is too large"
- ✅ **Right problem:** "CC wastes context finding things in the file"

A code map fixes the right problem without touching any code. Zero risk. Immediate ROI on every CC task.

## What the map is

A single markdown file at `app/CODE_MAP.md` (in the repo, lives next to `app/index.html`) containing 4 indexes:

1. **Tab index** — every UI tab → its code locations (inline + modules)
2. **Function index** — every top-level function → location + tab association
3. **Module index** — every extracted module → public API + dependencies
4. **Global index** — every shared global state object → declared at + consumed by

The map is human-readable markdown with structured tables. CC reads it natively, no parsing needed. Humans (Murad) can also read + edit it.

## How CC will use it

Required first step for ANY CC task on this codebase:

```
1. Read app/CODE_MAP.md  (~5K lines, fits in context budget)
2. Look up the relevant tab/function for the task
3. Read ONLY the specific section indicated:
   - If extracted: read the module file (~500 lines)
   - If inline: read the specific line range in app/index.html (~100 lines)
4. Make the edit
5. If function moved OR new function added: update CODE_MAP.md too
```

**Before:** CC reads CLAUDE.md + greps + reads 5000 lines of index.html before knowing where to edit.
**After:** CC reads CODE_MAP.md (small) + reads 100-500 lines of target code. Total context usage drops ~80%.

## Comparison: old vs new workflow

### Scenario: "Fix the K+A KPI on dashboard for federal tier"

**Old way:**
1. CC greps for "K+A" → 50 hits across index.html
2. CC reads 5 chunks of 500 lines each = 2500 lines of context
3. CC figures out which chunk is dashboard
4. CC eventually finds + fixes the bug
5. Total context: ~3000 lines

**New way:**
1. CC reads `app/CODE_MAP.md` (~5000 lines, but compressed structured data)
2. Sees "Dashboard tab → K+A logic in `dashboard/dashboard-tab-kpi.js`"
3. Reads that one file (~500 lines)
4. Fixes the bug
5. Total context: ~5500 lines (but most of map is light table rows)

**The win isn't fewer lines — it's TARGETED lines.** CC's reasoning is on the right code, not on irrelevant chunks.

### Scenario: "Extract email notification sub-cluster"

**Old way:** CC greps for email functions, reads scattered chunks, guesses at boundaries, often aborts because anchor names don't match speculation.

**New way:** CC reads CODE_MAP → "Notifications tab" section lists exactly which functions are inline + their line ranges + what's already extracted. Boundaries are explicit. CC picks the next safe slice.

## Maintenance strategy — living document principle

The map is REWRITTEN constantly. It's not generated once and left alone — every PR that touches code updates it. This is enforced via 5 mandatory policies in `CLAUDE.md`:

### The 5 policies (codified in CLAUDE.md by Lane 000)

1. **Read the map first** — before any code task. The map tells you where to look, then you read only that section.
2. **Extract-on-touch** — when you modify a function that's a good extraction candidate (>100 LOC, cohesive cluster, clean diff possible), extract it to a module in the same commit. No separate refactor pass.
3. **Update map after every code change** — PR diff must include `app/CODE_MAP.md` changes if any function moved/added/renamed/deleted. PRs without map updates are rejected.
4. **Map drift is a bug** — if you find the map says L###, but code is at L###+50, fix the map in the same PR.
5. **Living document** — never trust line numbers blindly (re-grep), but always trust structure (which tab, which module).

### Why extract-on-touch matters

This is the key insight that replaces the failed "modular refactor effort":

| Old way (dedicated refactor) | New way (extract-on-touch) |
|---|---|
| Plan a "Phase 4" with 6 sessions of extractions | Each PR fixes a bug AND extracts the function it touched |
| 50-100 hours of dedicated CC time | Refactoring happens as a free side effect of normal work |
| The 92 already-extracted modules cost ~6 days of CC effort | The next 92 extractions cost zero dedicated time |
| Risk: extractions can break things, need smoke tests | Risk minimized — each extraction is in a PR with a real test (the bug fix or feature works) |

The map shrinks the inline code organically. After 6 months of normal feature work, the residual inline code will be just the genuinely tricky/shared stuff that doesn't lend itself to extraction.

### Three maintenance layers

| Layer | Trigger | Who | What |
|---|---|---|---|
| **Per-PR (primary)** | Every PR that touches code | CC, per CLAUDE.md Policy 3 | Updates affected map entries in the same diff |
| **Auto-regen (safety net)** | Manual run or post-batch (future work) | `scripts/regen-code-map.js` | Re-scans entire codebase, rewrites all 4 indexes from scratch |
| **Cowork sweep (rarely needed)** | When drift accumulates | Me (Cowork) | Reads latest via raw GitHub, fixes drift |

The map can have minor drift between regens — that's OK. CC's standard `§0 grep` step in every prompt verifies anchors before editing. If they don't match, CC updates the map.

## Integration with the existing federal-sync-and-verify skill

The skill's Step 2 (source-level verify via raw GitHub) gets a new sub-step:

> 2c. Read `app/CODE_MAP.md` first to identify the affected sections. Cross-check against the live `app/index.html` only for the relevant ranges. Skip the rest of the file.

This dramatically speeds up verification too.

## Failure modes covered

| Failure | Detection | Recovery |
|---|---|---|
| Map says function is at L###, but it's not there | CC's `§0 grep` catches mismatch | CC re-greps + updates map |
| Function moved to a module but map still says inline | Same — grep catches | Same |
| Tab renamed | Regen script catches | Run regen |
| New function added but not in map | Next regen catches | Run regen |
| Heuristic association wrong (function tagged with wrong tab) | Manual review | Edit map directly |

The map is **descriptive, not prescriptive**. CC doesn't BLINDLY trust it — verifies before editing.

## Cost-benefit

| Item | Cost | Benefit |
|---|---|---|
| First-time generation | ~30 min CC run | Map ready forever |
| Per-PR update | 5 min CC adds to its work | Map stays accurate |
| Auto-regen script | One-time write | Catches drift |
| Reading map in every CC task | ~5K lines of context | Saves 50-90% context per task |

**Net: massive win** if we do >10 more CC tasks (we will — there's months of work ahead).
